## 1. Introduction

A desktop program is born into a comfortable world: an operating system loads
it, gives it a stack, zeroes its globals, provides `printf`, and catches it if
it crashes. Bare-metal firmware has none of that. When reset is released the
CPU starts fetching from one fixed address and everything else is up to you:

- **Where does the code go?** The linker decides, guided by a linker script.
- **Who sets up the stack and zeroes globals?** A few lines of startup assembly.
- **How do I talk to hardware?** By reading and writing magic addresses.
- **How do I print?** There is no `printf`; you build your own output path.

This tutorial answers each of those questions for the SoC in this repository:

```text
 PicoRV32 ──AXI4-Lite──► router 0 ─── router 1 ──► RAM   (AXI4-Lite)
 (cpu clk)                  │            │
                         router 2 ─── router 3
                            │            │
                          Timer        GPIO          (APB, periph clk)
```

| Part | What it is |
|---|---|
| CPU | [PicoRV32](https://github.com/YosysHQ/picorv32), RV32I, AXI4-Lite master |
| NoC | 2x2 mesh generated by `networkOnChip/autoConfiguration/nocGen.py` |
| RAM | 16 KiB AXI4-Lite SRAM ([../rtl/axiLiteSram.sv](../rtl/axiLiteSram.sv)) |
| Timer | PULP `apb_timer`, two 32-bit timers |
| GPIO | PULP `apb_gpio`, 32 pads |

The tutorial does not teach the RISC-V instruction set in depth; the
instructions you need are summarised in [Appendix A](#appendix-a-rv32i-cheat-sheet).

## 2. Setting up the Lab

There is no board. The "hardware" is the RTL of the SoC, simulated cycle by
cycle with Verilator. You need:

| Tool | Used for |
|---|---|
| RISC-V GCC (`riscv64-unknown-elf-*`) | compile, assemble, link, inspect |
| Python 3 | `makehex.py`, `nocGen.py` |
| Verilator 5 + a C++20 compiler | simulate the SoC |
| gtkwave (optional) | view waveforms |

A `riscv64-unknown-elf` toolchain can build 32-bit code: you only need to
pass `-march=rv32i -mabi=ilp32`.

Everything is driven from the top-level [Makefile](../Makefile). Tool
locations are passed on the command line so the repository stays portable:

```sh
make sim RISCV_PREFIX=/path/to/bin/riscv64-unknown-elf- CXX=/path/to/g++
```

| Target | Does |
|---|---|
| `make firmware` | build `build/firmware/firmware.{elf,lst,bin,hex}` |
| `make noc` | generate the NoC RTL into `generated/` |
| `make sim` | build the simulator and run the firmware on it |
| `make sim SIM_ARGS=+traceRam` | also log every RAM access |
| `make waves` | as `sim`, plus a waveform in `build/waves.fst` |

## 3. Hello SoC

### 3.1. Building the Binary

`make firmware` runs four steps. Run them by hand once to see what each
produces (set `RV` to your toolchain prefix):

```sh
# 1. compile + assemble + link: C and assembly in, ELF executable out
${RV}gcc -march=rv32i -mabi=ilp32 -O2 -ffreestanding -fno-builtin -nostdlib \
    -T firmware/link.ld -o firmware.elf firmware/start.S firmware/main.c

# 2. disassemble, so humans can read what the CPU will execute
${RV}objdump -d firmware.elf > firmware.lst

# 3. strip the ELF wrapper: just the bytes, starting at address 0
${RV}objcopy -O binary firmware.elf firmware.bin

# 4. one 32-bit little-endian word per line, padded to the RAM depth
python3 firmware/makehex.py firmware.bin 4096 > firmware.hex
```

| File | What it is |
|---|---|
| `firmware.elf` | Executable plus metadata: sections, symbols, addresses |
| `firmware.lst` | Disassembly: address, machine word, assembly |
| `firmware.bin` | Raw memory image, byte 0 = address 0 |
| `firmware.hex` | `$readmemh` format: line *n* = RAM word *n* (address `4*n`) |

`size` gives the footprint:

```text
   text    data     bss     dec     hex filename
   2010       0      20    2030     7ee firmware.elf
```

About 2 KiB of code and constant strings, 20 bytes of zero-initialised
globals, and no initialised data.

### 3.2. Executing in the Simulator

The testbench ([../tb/tb_soc.sv](../tb/tb_soc.sv)) plays the role of the
board. It generates the clocks, holds reset, loads the hex file straight into
the RAM array:

```systemverilog
$readmemh(firmwareFile, u_soc.u_ram.mem);
```

and then lets the CPU run. `make sim` prints:

```text

RAM: word/halfword/byte stores (WSTRB through the NoC)
  [ OK ] word store = 0x11223344
  [ OK ] byte store lane 1 = 0x1122aa44
  ...
ALL TESTS PASSED
[tb] firmware done after 179416 CPU cycles (1435428 ns)
[tb]   CPU->RAM: 7000 reads (fetch+load), 75 writes
[tb]   CPU->timer/GPIO: 36 accesses
[tb] PASS
```

### 3.3. Watching the CPU Boot

Run `make sim SIM_ARGS=+traceRam`. Every RAM access the CPU makes is logged.
The very first lines are the CPU fetching the start-up code from address 0:

```text
[bus] 276 ns RD RAM   0x00000000 = 0x00004117
[bus] 452 ns RD RAM   0x00000004 = 0xff010113
[bus] 636 ns RD RAM   0x00000008 = 0x7dc00293
[bus] 812 ns RD RAM   0x0000000c = 0x7f000313
[bus] 996 ns RD RAM   0x00000010 = 0x0062f863
```

Compare with the first words of `firmware.hex` and the first lines of
`firmware.lst`:

```text
00000000 <_start>:
   0:   00004117    auipc   sp,0x4
   4:   ff010113    addi    sp,sp,-16 # 3ff0 <_stack_top>
   8:   7dc00293    li      t0,2012
   c:   7f000313    li      t1,2032
```

The same four words appear in all three places. The hex file is what is in
RAM, the listing tells you what those words mean, and the trace shows the CPU
actually reading them. Note the spacing: a new instruction every ~180 ns, or
~22 CPU cycles. That is one round trip through the NoC per fetch, which is
the price of executing straight out of a RAM that lives on another router.

## 4. The Programmer's Model

### 4.1. Registers

RV32I has 32 general-purpose 32-bit registers, `x0`..`x31`, plus the program
counter `pc`. `x0` always reads as zero. The assembler uses ABI names that
describe how the C calling convention uses each register:

| ABI name | Register | Role |
|---|---|---|
| `zero` | `x0` | constant 0 |
| `ra` | `x1` | return address |
| `sp` | `x2` | stack pointer |
| `t0`-`t6` | | temporaries (caller-saved) |
| `s0`-`s11` | | saved registers (callee-saved) |
| `a0`-`a7` | | function arguments and return values |

You will see this in the listing: `check(name, got, expected)` is called with
`name` in `a0`, `got` in `a1` and `expected` in `a2`.

### 4.2. Memory Map

The CPU sees a flat 32-bit address space. Which device answers depends only on
the address, and that mapping lives in the NoC, generated from
[../config/socNoc.json](../config/socNoc.json):

| Address range | Device | NoC router |
|---|---|---|
| `0x0000_0000 - 0x0000_3FFF` | RAM, 16 KiB | 1 |
| `0x4000_0000 - 0x4000_0FFF` | Timer | 2 |
| `0x4000_1000 - 0x4000_1FFF` | GPIO | 3 |
| anything else | nothing: the NoC answers `DECERR` | - |

### 4.3. Reset State

[../rtl/socTop.sv](../rtl/socTop.sv) configures PicoRV32 with:

| Parameter | Value | Effect |
|---|---|---|
| `PROGADDR_RESET` | `0x0000_0000` | first fetch after reset |
| `STACKADDR` | `0x0000_3FF0` | `sp` preset at reset |
| `ENABLE_IRQ` | 0 | no interrupts: a fault halts the CPU (`o_cpuTrap`) |
| `COMPRESSED_ISA` | 0 | 32-bit instructions only |

Everything else, including all other registers, is undefined at reset.

## 5. From C to Loads and Stores

### 5.1. Every Memory Access is a Load or a Store

RISC-V is a load/store architecture. Arithmetic only works on registers; the
only instructions that touch memory are loads (`lw`, `lh`, `lhu`, `lb`,
`lbu`) and stores (`sw`, `sh`, `sb`). The address is always
`register + 12-bit signed offset`.

So whenever C *reads* a variable that lives in memory, the compiler emits a
load, and whenever C *writes* one, it emits a store. The width comes from the
C type: `uint32_t` → `lw`/`sw`, `uint16_t` → `lhu`/`sh`, `uint8_t` → `lbu`/`sb`.

### 5.2. Worked Example: `testRam()`

```c
static volatile uint32_t scratch[4];

static void testRam(void)
{
  volatile uint8_t *bytes = (volatile uint8_t *)scratch;
  volatile uint16_t *halves = (volatile uint16_t *)scratch;

  scratch[0] = 0x11223344u;
  check("word store", scratch[0], 0x11223344u);
  bytes[1] = 0xAAu;
  check("byte store lane 1", scratch[0], 0x1122AA44u);
  halves[1] = 0xBEEFu;
  check("halfword store upper", scratch[0], 0xBEEFAA44u);
  check("byte load lane 3", bytes[3], 0xBEu);
}
```

The linker placed `scratch` at `0x7DC` (see [section 8](#8-the-linker)).
`bytes` and `halves` generate no code at all: they are the same address seen
through different types. The compiler loads the address into `s0` once and
uses different offsets and widths:

| C | Address | Instruction |
|---|---|---|
| `scratch[0] = ...` | `s0 + 0` | `sw` |
| `bytes[1] = ...` | `s0 + 1` | `sb` |
| `halves[1] = ...` | `s0 + 2` | `sh` |
| `bytes[3]` (read) | `s0 + 3` | `lbu` |

From `firmware.lst` (`testRam` was inlined into `main`):

```text
1a0: lui   a2,0x11223      # build the constant 0x11223344 ...
1a4: li    s0,2012         # s0 = &scratch[0] = 0x7DC
1a8: addi  a2,a2,836       # ... a2 = 0x11223344
1ac: sw    a2,0(s0)        # scratch[0] = 0x11223344
1b0: lw    a1,0(s0)        # got = scratch[0]
1b4: li    a0,1716         # name = "word store" (address of the string)
1b8: jal   ra,74 <check>   # check(a0, a1, a2)
1bc: li    a5,-86          # 0xAA
1c0: sb    a5,1(s0)        # bytes[1] = 0xAA
1c4: lw    a1,0(s0)        # got = scratch[0]
 ...
1e0: sh    a5,2(s0)        # halves[1] = 0xBEEF
 ...
1f8: lbu   a1,3(s0)        # got = bytes[3]
```

RISC-V is little-endian, so the bytes at `0x7DC..0x7DF` evolve like this:

| After | Bytes 0..3 | Word |
|---|---|---|
| `sw 0x11223344` | `44 33 22 11` | `0x11223344` |
| `sb 0xAA` at +1 | `44 AA 22 11` | `0x1122AA44` |
| `sh 0xBEEF` at +2 | `44 AA EF BE` | `0xBEEFAA44` |

### 5.3. Why `volatile`

Without `volatile` the compiler is allowed to notice that it just stored
`0x11223344` and pass that constant straight to `check()` with no `lw` at all.
The test would pass without ever touching the NoC. `volatile` tells the
compiler that the memory may change or have side effects behind its back, so
every read and write in the source must appear, in order, in the binary.

For RAM this is a testing choice. For peripheral registers it is mandatory
([section 12](#12-talking-to-peripherals)).

## 6. From Loads and Stores to AXI

### 6.1. The Native Bus

Inside `picorv32_axi`, the core talks to a simple bus, one transfer at a time:

| Signal | Meaning |
|---|---|
| `mem_valid` | a transfer is requested; held until `mem_ready` |
| `mem_instr` | it is an instruction fetch |
| `mem_addr` | word-aligned address |
| `mem_wdata`, `mem_wstrb` | write data and byte enables; `wstrb == 0` means read |
| `mem_ready`, `mem_rdata` | transfer complete, read data |

`picorv32_axi_adapter` maps that onto AXI4-Lite almost combinationally:

```verilog
awvalid = mem_valid &&  |mem_wstrb && !ack_awvalid;   // store
wvalid  = mem_valid &&  |mem_wstrb && !ack_wvalid;
arvalid = mem_valid && !mem_wstrb  && !ack_arvalid;   // load or fetch
awaddr  = araddr = mem_addr;
mem_ready = bvalid || rvalid;
```

### 6.2. A Store (`sw`)

```text
mem_valid   __|‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾|____
awvalid     __|‾‾‾‾‾|____________________________   awaddr 0x7DC
wvalid      __|‾‾‾‾‾|____________________________   wdata 0x11223344, wstrb 1111
awready     ________|‾|__________________________   NoC accepts AW and W together
wready      ________|‾|__________________________
bvalid      ____________________________|‾|______   response after the round trip
mem_ready   ____________________________|‾|______   core retires the sw
```

The CPU stalls until `bvalid`: the store is not complete until the RAM, two
routers away, has acknowledged it.

### 6.3. A Load (`lw`) and a Fetch

```text
mem_valid   __|‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾|____
arvalid     __|‾‾‾‾‾|____________________________   araddr 0x7DC
arready     ________|‾|__________________________
rvalid      ____________________________|‾|______   rdata 0x11223344
mem_ready   ____________________________|‾|______   core writes a1
```

An instruction fetch is the same read, with `araddr = pc` and
`arprot = 3'b100`.

### 6.4. Narrow Stores and Byte Strobes

PicoRV32 always sends the word-aligned address. For `sb`/`sh` it replicates
the data across the byte lanes and uses `wstrb` to mark the bytes that count.
The `+traceRam` log for `testRam()` shows exactly this:

```text
[bus] 133444 ns WR RAM   0x000007dc = 0x11223344 strb 1111    sw
[bus] 133956 ns RD RAM   0x000007dc = 0x11223344              lw
[bus] 186156 ns WR RAM   0x000007dc = 0xaaaaaaaa strb 0010    sb  +1
[bus] 186668 ns RD RAM   0x000007dc = 0x1122aa44              lw
[bus] 248068 ns WR RAM   0x000007dc = 0xbeefbeef strb 1100    sh  +2
[bus] 248580 ns RD RAM   0x000007dc = 0xbeefaa44              lw
```

The NoC must carry `wstrb` all the way to the RAM, and the RAM must update
only the strobed lanes. If either got it wrong, the `sb` would overwrite the
whole word with `0xAAAAAAAA` and the "byte store lane 1" check would fail.
That is precisely what `testRam()` is there to catch.

You will also spot stack traffic in the trace, e.g.
`WR RAM 0x00003fb8 = 0x000007dc`: `check()` is a real call, so the compiler
saves `s0` on the stack (just below `0x3FF0`) and restores it afterwards.

## 7. Across the NoC

What happens between `awvalid` and `bvalid`? The CPU's AXI port is not wired to
the RAM. It is wired to a **network interface (NI)** on router 0:

1. **Decode.** `niAxiLiteInitiator` compares the address with the address map
   baked into the generated `nocSoc.sv`. `0x7DC` matches the RAM entry →
   destination router (row 0, col 1). An address that matches nothing is
   answered immediately with `DECERR` and never enters the mesh.
2. **Packetise.** Address, data, strobes and the source coordinates are
   packed into one packet. Because the SoC mixes AXI4-Lite and APB targets,
   a 2-bit protocol opcode is prepended.
3. **Cross clocks.** The CPU runs on `cpuClk`, the mesh on `fabricClk`. A
   `cdcNiBridge` (two asynchronous FIFOs) carries the packet across.
4. **Route.** Routers forward the packet with dimension-ordered XY routing.
   Router 0 (0,0) → router 1 (0,1) is one hop east.
5. **Deliver.** `niAxiLiteTarget` on router 1 unpacks the packet and replays
   it as an AXI4-Lite write into `axiLiteSram`.
6. **Respond.** The RAM's B response is packed and routed back to (0,0),
   crosses back into `cpuClk`, and comes out of the initiator NI as `bvalid`.

For the timer and GPIO the trip is longer: their target routers host an
`apbTargetBridge`, which converts the AXI4-Lite request to an APB transfer,
and a second CDC into `periphClk`.

You can measure the cost directly in the trace: back-to-back instruction
fetches are ~22 CPU cycles apart, and a peripheral access is visibly slower
than a RAM one. That is the whole demonstration in one number: ordinary
firmware runs unchanged, but every access is a packet.

## 8. The Linker

### 8.1. Symbol Resolution

The compiler compiles `start.S` and `main.c` separately. `start.S` contains
`call main` but has no idea where `main` will be; `main.c` uses the string
`"word store"` but does not know its final address. Each object file only
holds *references*. The linker collects all the pieces, assigns every
section and symbol a final address, and patches every reference. `nm` lists
the result:

```text
$ ${RV}nm -n build/firmware/firmware.elf
00000000 T _start
00000010 t clear_bss
00000020 t run_main
00000024 t halt
00000028 t putHex
00000074 t check
0000014c T main
000007dc B _bss_start
000007dc b scratch
000007ec b errors
000007f0 B _bss_end
00003ff0 A _stack_top
```

(`T`/`t` = code, `B`/`b` = `.bss`, `A` = absolute; upper case = global.)
`putChar` and `putStr` are missing because the compiler inlined them.
`_bss_start`, `_bss_end` and `_stack_top` are not in any source file: the
linker script defines them.

### 8.2. Relocation

After addresses are fixed, the linker rewrites instructions that refer to
them. That is how `call main` in `start.S` became

```text
20: 12c000ef    jal  ra,14c <main>
```

`0x14c - 0x20 = 0x12c`: the jump offset was filled in by the linker. The same
mechanism turned `la t0, _bss_start` into `li t0,2012`: once the linker knew
the symbol was a small absolute value (`0x7DC`), it replaced the general
`auipc`+`addi` sequence with a single `li` ("linker relaxation").

## 9. The Linker Script

[link.ld](link.ld) tells the linker *where* things go. Without it, GCC
would place code at an address suitable for a Linux program, and the CPU,
which always starts at 0, would fetch garbage.

```ld
OUTPUT_ARCH("riscv")
ENTRY(_start)
```

`ENTRY` names the entry point. It is recorded in the ELF header, but the CPU
never reads ELF headers. What really makes `_start` run first is that it is
*placed* at the reset address, which the next part arranges.

```ld
MEMORY
{
  RAM (rwx) : ORIGIN = 0x00000000, LENGTH = 0x3000
}

_stack_top = 0x3FF0;
```

`MEMORY` declares the region the linker may fill: the first 12 KiB of RAM.
If the program outgrows it, the link fails instead of silently colliding with
the stack. `_stack_top` is just a symbol definition with a value; no memory
is allocated.

```ld
SECTIONS
{
  .text : {
    *(.text.start)
    *(.text .text.*)
  } > RAM
```

Output section `.text` is built from the input sections of every object file,
in the order listed. `.text.start` (only `start.S` uses that name) goes
**first**, so `_start` lands at `0x0`. Then all other code follows.

```ld
  .rodata : { *(.rodata .rodata.* .srodata .srodata.*) } > RAM
  .data   : { *(.data .data.* .sdata .sdata.*) } > RAM
  .bss (NOLOAD) : {
    . = ALIGN(4);
    _bss_start = .;
    *(.bss .bss.* .sbss .sbss.* COMMON)
    . = ALIGN(4);
    _bss_end = .;
  } > RAM

  /DISCARD/ : { *(.comment) *(.riscv.attributes) }
}
```

`.` is the location counter, the address the linker is currently filling.
Assigning it to a symbol (`_bss_start = .;`) exports that address to the
program. `/DISCARD/` drops compiler metadata so it does not end up in the
binary.

The result, from `readelf -S`:

```text
  [ 1] .text    PROGBITS  00000000  size 0x51c
  [ 2] .rodata  PROGBITS  0000051c  size 0x2be
  [ 3] .bss     NOBITS    000007dc  size 0x014
```

and the RAM map:

```text
0x0000 ┌──────────────────────┐ ← reset, _start
       │ .text                │
0x051c │ .rodata  (strings)   │
0x07dc │ .bss     scratch[4]  │
0x07ec │          errors      │
0x07f0 ├──────────────────────┤ ← _bss_end
       │ (free)               │
       │   ↑ stack grows down │
0x3ff0 │ _stack_top           │
0x3ffc │ console mailbox      │
0x4000 └──────────────────────┘
```

## 10. Sections in RAM: .data and .bss

C has three kinds of global data, and each ends up in a different section:

| C | Section | In the image? |
|---|---|---|
| `const char msg[] = "hi";`, string literals | `.rodata` | yes |
| `int x = 5;` | `.data` | yes |
| `static uint32_t errors;` (no initialiser) | `.bss` | **no** |

`.bss` is marked `NOLOAD` (`NOBITS` in `readelf`): the linker reserves the
addresses but stores no bytes, because the content is all zeros by
definition. Somebody still has to *make* it zero before `main()` runs. That
is the start-up code's job ([section 11](#11-c-startup)).

### 10.1. Why this SoC needs no .data copy

On a typical microcontroller the program lives in flash, which the CPU cannot
write. `.data` must then be stored in flash (its *load address*) and copied
to RAM (its *run address*) by the start-up code. The GNU tutorial's
"Data in RAM" chapter is all about that.

Here, the testbench preloads the whole image directly into the RAM the CPU
executes from, so load address = run address and `.data` is already in
place. This firmware happens to have no `.data` anyway (`size` reports 0),
but if you add `uint32_t counter = 42;` it will just work.

> **If this were silicon:** RAM content is random at power-up and nothing
> preloads it. You would add a boot ROM on the NoC, link `.text`/`.rodata`
> there with `AT>` load addresses for `.data`, and copy `.data` in
> `start.S`. See [Exercise 6](#15-exercises).

## 11. C Startup

Compiled C code makes assumptions:

1. `sp` points at valid, writable memory, aligned to 16 bytes.
2. Globals without an initialiser read as zero.
3. Initialised globals hold their initial values.
4. Somebody calls `main`.

On a desktop the OS and the C runtime (`crt0`) take care of this. Here,
[start.S](start.S) does it in ten instructions:

```asm
  .section .text.start        # placed first by link.ld -> address 0
  .global _start
_start:
  la    sp, _stack_top        # assumption 1
  la    t0, _bss_start        # assumption 2: zero .bss word by word
  la    t1, _bss_end
clear_bss:
  bgeu  t0, t1, run_main
  sw    zero, 0(t0)
  addi  t0, t0, 4
  j     clear_bss
run_main:
  call  main                  # assumption 4
halt:
  j     halt                  # nowhere to return to
```

Assumption 3 needs nothing because the image is preloaded
([section 10.1](#101-why-this-soc-needs-no-data-copy)).

Some details worth noticing:

- **`la sp, _stack_top`** assembled to `auipc sp,0x4` + `addi sp,sp,-16`: the
  address is computed relative to `pc` (`0 + 0x4000 - 16 = 0x3FF0`).
  PicoRV32's `STACKADDR` already presets `sp`, so this is belt and braces,
  but it keeps the firmware correct on any core configuration.
- **The `.bss` loop is visible on the bus.** In the `+traceRam` log you can
  watch it zero `0x7DC`, `0x7E0`, ... one NoC write at a time:

  ```text
  [bus] 1372 ns WR RAM   0x000007dc = 0x00000000 strb 1111
  [bus] 2268 ns WR RAM   0x000007e0 = 0x00000000 strb 1111
  ```

- **Why not `ret` from `_start`?** There is no caller. If `main` returns, the
  CPU spins on `j halt` forever. Real firmware usually never returns from
  `main` at all.

## 12. Talking to Peripherals

### 12.1. Memory-Mapped I/O

The timer and GPIO have no special instructions. Their registers simply occupy
addresses, and the CPU uses ordinary `lw`/`sw` on them. [soc.h](soc.h) gives
those addresses names:

```c
#define REG32(addr) (*(volatile uint32_t *)(addr))

#define GPIO_BASE 0x40001000u
#define GPIO_DIR  REG32(GPIO_BASE + 0x00u)
#define GPIO_OUT  REG32(GPIO_BASE + 0x0Cu)
```

`REG32(a)` turns a number into "the 32-bit volatile object at address `a`".
So `GPIO_DIR = x;` is a store to `0x40001000` and `y = GPIO_DIR;` is a load
from it:

```text
22c: lui  s0,0x40001        # s0 = GPIO_BASE
238: sw   a5,4(s0)          # GPIO_EN  = ...
240: sw   a2,0(s0)          # GPIO_DIR = ...
244: lw   a1,0(s0)          # ... = GPIO_DIR
258: sw   s1,12(s0)         # GPIO_OUT = ...
```

For peripherals `volatile` is not optional. Registers can change on their own
(the timer counts, `GPIO_IN` follows the pads) and reads can have side effects
(`GPIO_INT_STATUS` clears when read). The compiler must never cache, merge,
reorder or delete these accesses.

The NoC decodes `0x4000_1xxx` to router 3, the APB target bridge turns the
AXI4-Lite request into an APB `PSEL`/`PENABLE` transfer, and the GPIO sees
`PADDR[11:0] = 0x000`. The testbench logs every peripheral access:

```text
[bus] 440580 ns WR GPIO  0x40001000 = 0xc000ffff
[bus] 441412 ns RD GPIO  0x40001000 = 0xc000ffff OKAY
  [ OK ] DIR readback = 0xc000ffff
```

### 12.2. GPIO

Three buses connect the GPIO to the "board":

| Signal | Register | Meaning |
|---|---|---|
| `gpio_dir` | `PADDIR` | 1 = pad is an output |
| `gpio_out` | `PADOUT` (`SET`/`CLR` modify it) | value driven on output pads |
| `gpio_in` | `PADIN` | level on the pads, 2-flop synchronised |

Inputs are only sampled for pads enabled in `GPIOEN`. The testbench wires
pads 15:0 back from `gpio_out` to `gpio_in`, so `testGpio()` can write `OUT`
and read the same value back on `IN`. That proves both directions through the
NoC.

`SET` and `CLR` exist so firmware can change individual bits without a
read-modify-write. `GPIO_OUT_SET = 0x5A00` sets bits 9, 11, 12 and 14 in one
store. A plain `GPIO_OUT |= 0x5A00` would be a load, an `or` and a store,
which takes two NoC round trips and is not atomic.

### 12.3. Timer

Each timer has `COUNT` (+0x0), `CTRL` (+0x4: bit 0 enable, bits 5:3
prescaler) and `CMP` (+0x8). Timer *n* sits at `TIMER_BASE + 0x10*n`.
`testTimer()` stops the timer, loads `COUNT`, reads it back, then enables it
and checks it advances, first at full speed and then with a prescaler of 7
(one count per 8 periph clocks). The trace shows the difference:

```text
[bus] 937220 ns RD TIMER 0x40000000 = 0x00002201    prescaler 0
[bus] 945284 ns RD TIMER 0x40000000 = 0x00002441    +576 in ~8 us
[bus] 1003564 ns RD TIMER 0x40000000 = 0x00003467   prescaler 7
[bus] 1011628 ns RD TIMER 0x40000000 = 0x000034af   +72  in ~8 us (576 / 8)
```

### 12.4. Peripheral to Peripheral

When `COUNT` reaches `CMP`, the timer pulses its compare interrupt and
restarts. The testbench wires timer 1's compare output to GPIO pad 16.
`testTimerToGpioInterrupt()` configures pad 16 for a rising-edge interrupt,
starts the timer with `CMP = 100` and polls `GPIO_INT_STATUS` until bit 16
sets. The CPU has interrupts disabled, so this is a *polled* interrupt, but
it shows two peripherals on the periph clock cooperating while the CPU
watches them through the NoC.

### 12.5. When Nobody Answers

```c
(void)REG32(0x80000000);
```

No address-map entry covers `0x8000_0000`, so the CPU's NI answers on its own
with `RRESP = DECERR` and the access completes:

```text
[bus] 1351932 ns RD NONE  0x80000000 = 0x00000000 DECERR
```

PicoRV32 ignores `RRESP`, so the CPU carries on with a value of 0. A bus that
simply never responded would hang the CPU forever.

## 13. A Console without a UART

There is no UART, yet the firmware prints. The trick is a **mailbox**: the
last word of RAM, `0x3FFC`.

```c
static void putChar(char c)
{
  *(volatile uint8_t *)CONSOLE_ADDR = (uint8_t)c;
}
```

This is an ordinary `sb` to `0x3FFC`:

```text
38: fee68e23    sb  a4,-4(a3)     # a3 = 0x4000, so the address is 0x3FFC
```

The testbench watches the CPU's write channel and, whenever `awaddr` is
`0x3FFC`, prints `wdata[7:0]` as a character instead of logging a RAM write:

```systemverilog
if (u_soc.cpuAwaddr == CONSOLE_ADDR)
  $write("%c", u_soc.cpuWdata[7:0]);
```

The store still really happens, crossing the NoC into RAM like any other.
The monitor merely *observes* it. Swapping this for a real UART later only
means changing `putChar()`.

On top of `putChar` sit `putStr` and `putHex`. `putHex` prints hex with
shifts and masks only, for a reason explained next.

## 14. Building without a C Library

The compile flags in the Makefile are:

```text
-march=rv32i -mabi=ilp32 -O2 -ffreestanding -fno-builtin -nostdlib
```

| Flag | Why |
|---|---|
| `-march=rv32i -mabi=ilp32` | the exact ISA PicoRV32 is built with: no `M`, `A`, `C`, `F` |
| `-ffreestanding` | no hosted environment: `main` is not special, no `<stdio.h>` |
| `-fno-builtin` | do not turn loops into calls to `memset`/`memcpy` that do not exist |
| `-nostdlib` | link no C library, no `crt0`, **and no `libgcc`** |

The available toolchain has no plain `rv32i` multilib, so its `libgcc` and
`newlib` are built for other ISAs and cannot be used safely. The consequence:
RV32I has no multiply or divide instruction, and without `libgcc` there are
no software routines (`__mulsi3`, `__udivsi3`) either. **Any `*`, `/` or `%`
on a non-constant in the firmware will fail to link.** That is why `putHex`
uses `>>` and `&` instead of `/ 16` and `% 16`, and why `soc.h` computes
register offsets with shifts.

Check for accidental libgcc calls with:

```sh
grep -E "__|mul|div" build/firmware/firmware.lst
```

## 15. Exercises

1. **Blink.** Make pad 0 toggle forever, using `TIMER_COUNT` to pace it. Run
   `make waves` and find `gpioOut[0]` in gtkwave.
2. **Count the cost.** Read `rdcycle` (PicoRV32 is built with
   `ENABLE_COUNTERS`) before and after a single `GPIO_IN` read, and print the
   difference. Compare with a `scratch[0]` read. That gives you the NoC
   latency of an APB versus an AXI4-Lite target, measured by firmware.
3. **Initialised data.** Add `static uint32_t magic = 0xCAFEF00D;`, print it,
   and find it in `readelf -S` (a `.data` section appears) and in
   `firmware.hex`.
4. **Break the build.** Add `uint32_t x = a * b;` with non-constant operands
   and read the link error. Then implement your own `__mulsi3` with shifts
   and adds.
5. **Trap.** Add `asm volatile ("ebreak");` and watch the testbench report
   `FAIL: CPU trapped`. Why does the core halt rather than jump to a handler?
   (Hint: `ENABLE_IRQ`.)
6. **Boot from ROM.** Add a second target to `config/socNoc.json` (a
   read-only AXI4-Lite ROM at `0x1000_0000`), set `PROGADDR_RESET` there,
   link `.text`/`.rodata` to ROM and `.data`/`.bss` to RAM with `AT>`, and
   add the `.data` copy loop to `start.S`.
7. **Move the RAM.** Change the RAM's router in `config/socNoc.json` from 1 to
   3 (and GPIO to 1), rerun `make sim`, and compare the cycle count. The
   firmware does not change; only the distance does.

## Appendix A. RV32I Cheat Sheet

The instructions that appear in `firmware.lst`:

| Instruction | Meaning |
|---|---|
| `lui rd, imm` | `rd = imm << 12` |
| `auipc rd, imm` | `rd = pc + (imm << 12)` |
| `addi rd, rs, imm` | `rd = rs + imm` (12-bit signed) |
| `li rd, imm` | pseudo: load constant (`addi` and/or `lui`) |
| `la rd, sym` | pseudo: load address (`auipc`+`addi`, or `li` after relaxation) |
| `mv rd, rs` | pseudo: `addi rd, rs, 0` |
| `lw/lh/lb rd, off(rs)` | load word/half/byte, sign-extended |
| `lhu/lbu rd, off(rs)` | load half/byte, zero-extended |
| `sw/sh/sb rs2, off(rs1)` | store word/half/byte |
| `and/or/xor/sll/srl/sra` | bitwise and shifts (also `...i` immediate forms) |
| `beq/bne/blt/bge/bltu/bgeu` | compare and branch |
| `bnez/beqz` | pseudo: branch if (not) zero |
| `jal rd, label` | `rd = pc + 4; pc = label` (`call`, `j`) |
| `jalr rd, off(rs)` | `rd = pc + 4; pc = rs + off` (`ret`) |
| `ecall/ebreak` | environment call/breakpoint: traps on this SoC |

## Appendix B. Register Maps

**Timer** (`0x4000_0000`, timer *n* at `+0x10*n`)

| Offset | Name | Notes |
|---|---|---|
| `0x0` | `COUNT` | current count; writable |
| `0x4` | `CTRL` | bit 0 enable; bits 5:3 prescaler (count every *p*+1 clocks) |
| `0x8` | `CMP` | compare value; writing it resets `COUNT`; 0 disables compare |

**GPIO** (`0x4000_1000`)

| Offset | Name | Notes |
|---|---|---|
| `0x00` | `PADDIR` | 1 = output |
| `0x04` | `GPIOEN` | 1 = sample this pad's input |
| `0x08` | `PADIN` | synchronised input levels (read-only) |
| `0x0C` | `PADOUT` | output values |
| `0x10` | `PADOUTSET` | write 1s to set `PADOUT` bits |
| `0x14` | `PADOUTCLR` | write 1s to clear `PADOUT` bits |
| `0x18` | `INTEN` | per-pad interrupt enable |
| `0x1C` | `INTTYPE` pads 0-15 | 2 bits/pad: 00 fall, 01 rise, 10 both |
| `0x20` | `INTTYPE` pads 16-31 | same |
| `0x24` | `INTSTATUS` | pending edges; cleared on read |

**Board wiring** (in the testbench)

| Pad | Connection |
|---|---|
| 15:0 | `gpio_out` looped back to `gpio_in` |
| 16 | timer 1 compare interrupt |
| 30 | firmware "pass" |
| 31 | firmware "done": ends the simulation |
